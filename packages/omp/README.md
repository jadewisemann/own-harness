# OMP work 플러그인

작업을 대화로 정의하고 저장소별 Git worktree를 준비합니다. 작업 지침을 구성하고, omp 훅으로 문서 준비 상태와 지원되는 파일 도구의 변경 경로를 검사합니다. OMP 18.8.3의 확장 API를 기준으로 작성했습니다.

```text
workspace/
├── repository/
│   ├── frontend/
│   └── backend/
└── work/
    └── feature-a/
        ├── task.md
        ├── AGENTS.md          # 공통 지침의 최초 사본과 작업 운영 규칙
        ├── .work-rules/       # 저장소별 지침의 최초 사본
        ├── frontend/
        ├── backend/
        └── .sub-workspace/  # omp가 생성·반영·정리하는 임시 격리 공간
```

## 연결과 사용

저장소 루트에서 사용자 플러그인으로 연결한 뒤 새 omp 세션을 시작합니다. 아래 경로는 예시입니다. 플러그인은 소스 폴더를 직접 연결하므로 소스 폴더를 유지하세요. 상태 해석 파일을 Codex 배포본과 함께 사용하므로 `packages/omp/`만 따로 복사하지 말고 저장소 또는 CI 배포 묶음의 폴더 구조를 유지하세요.

```sh
omp plugin link ./packages/omp --scope user
omp --cwd /absolute/path/workspace
```

플러그인을 등록한 상태에서는 같은 확장을 `-e`로 추가하지 않습니다. 설치된 omp가 심볼릭 링크 경로와 원본 경로를 별개로 탐색할 수 있기 때문입니다. 생성한 재개 명령은 등록된 플러그인을 사용합니다.

omp 입력창에서 `/work-init`만 실행하면 작업을 정리하는 대화를 시작합니다. 아이디어를 덧붙여도 됩니다.

```text
/work-init
/work-init 로그인 실패 시 안내를 개선하고 싶어
```

에이전트가 해결할 문제와 원하는 결과를 듣고, 범위·비목표·완료 조건을 함께 정리합니다. 저장소와 로컬 ref를 확인해 사용할 저장소·기준 브랜치도 제안합니다. 이 단계에서는 작업 폴더를 생성하지 않습니다. workspace 루트에는 `.own-harness-workspace.json`을 만들어 이 workspace의 훅 검사를 활성화합니다.

이름은 `26-10-08__01__improve-login`처럼 **한국 날짜(YY-MM-DD) + 그날의 두 자리 순번 + 영문 소문자·하이픈 설명**으로 제안합니다. 기존 작업 이름의 최대 순번 다음 값을 사용하며, 삭제한 번호 사이의 빈자리는 채우지 않습니다. 작업 번호는 하루 01~99, 전체 이름은 64자까지입니다. 설명 부분은 사용자와 대화하며 정합니다.

대화가 정리되면 에이전트가 `work_create` 도구를 호출합니다. 이름·저장소·작업 문서 초안을 사용자가 확인하는 화면이 나타나고, 확인하면 생성합니다. 취소하면 생성하지 않고 대화를 이어갈 수 있습니다. `/work-init`으로 시작한 부모 세션과 사용자 확인 UI가 필요합니다.

생성은 저장소·기준 ref·브랜치 충돌을 검사한 뒤 진행합니다. 로컬에 있는 ref의 커밋을 기준으로 각 저장소에 `work/<작업명>` 브랜치를 만듭니다. 원격 fetch나 원본의 미커밋 변경 복사는 하지 않습니다. 생성 중 실패하면 만들어진 파일과 worktree를 보존하고 오류를 표시합니다. 재실행으로 덮어쓰거나 자동 삭제하지 않습니다.

기존 명시적 생성 문법 `/work-init feature-a frontend=origin/main backend=origin/main`도 유지합니다. 이 문법은 대화 없이 빈 작업 문서를 만듭니다. 기존 작업은 `/work-open 26-10-08__01__improve-login`처럼 다시 엽니다.

대화형 생성은 확인한 목표·범위·비목표·완료 조건·설계 결정과 미정 사항을 `task.md`에 저장합니다. 이 문서가 작업 범위의 아이디어·설계 정본이며, 프로젝트 전체의 DESIGN.md와 충돌하는 결정은 먼저 조정하도록 명시합니다. 진행 중에는 결정·검증 결과·다음 행동을 갱신합니다. 재개 명령은 이 파일을 `@파일` 인자로 다음 세션에 전달합니다. 원래 대화 전체나 세션 ID를 복사하지 않습니다.

생성 도구는 저장소별 실행 명령을 반환하고, `work-open`은 입력창에 실행 명령을 표시합니다. 명령을 터미널에서 실행하면 해당 worktree에서 새 omp 세션이 시작됩니다. 명시적인 `--session-dir <작업>/.sessions/<저장소>`를 사용하므로 자동 재개 설정이 켜져 있어도 새 세션을 만듭니다. 추가 파일과 문서는 작업 폴더에 둘 수 있습니다.

## 외부 상태 상속

`workspace/state.json` → `work/<task>/state.json` → 등록된 격리 workspace의 `state.json` 순서로 항목별 상속합니다. `mode`, `control`, `instruction`의 형식과 예시는 [공통 사용법](../../README.md#외부-상태-스티어링)을 참고하세요. 빠진 항목은 상위의 현재 값을 따르고 하위 지정 항목만 덮어씁니다.

서브 workspace는 부모 에이전트의 저장소 연결과 실제 Git worktree 등록을 확인한 뒤 선택합니다. OMP 내부 폴더 형태를 가정하지 않으며, 확인된 격리 checkout 루트가 서브 workspace입니다. Git이 추적하는 `state.json`은 제품 파일로 보고 무시합니다. 이 경우 부모 상태를 상속합니다. 일반 작업 checkout과 기준 저장소 안의 동명 파일도 제어 상태로 읽지 않습니다.

모델 실행 전과 매 도구 호출 때 최신 상태를 전달합니다. `human` 또는 잘못된 상태 파일에서는 읽기 전용 도구 외 실행과 서브에이전트 생성을 보류합니다. 셸은 읽기 명령도 보류합니다. `auto`에서도 기존 작업 문서·경로 검사를 유지합니다. 사용자의 요청 없이 에이전트가 상태를 바꾸어 차단을 해제하면 안 됩니다.

상태 파일 편집은 실행 중 명령을 중단하거나 이미 한 변경을 되돌리지 않습니다. 상태 파일을 삭제하면 다음 훅에서 상속된 값 또는 외부 지정 없음으로 돌아갑니다. 기존 AGENTS.md 최초 사본 보관과 `state.json`의 실시간 상속은 서로 다른 동작입니다.

## AGENTS.md 구성과 workspace 훅

- 생성 시 workspace에서 상위로 올라가며 AGENTS.md를 수집합니다. 홈 디렉터리 자체는 포함하지 않습니다. `repository/AGENTS.md`도 공통 지침에 포함합니다. 출처와 본문을 작업 AGENTS.md에 저장합니다.
- 저장소 루트의 지침은 worktree의 AGENTS.md를 우선하고, 없으면 원본 저장소의 파일을 사용합니다. 저장소별로 `.work-rules/<저장소>.md`에 보관합니다. 다른 저장소의 지침을 모델에 섞어 전달하지 않습니다. 하위 디렉터리의 별도 지침은 기존 저장소 규칙을 따릅니다.
- 기존 작업 AGENTS.md와 저장소별 사본은 덮어쓰지 않습니다. 상위 지침의 후속 변경도 자동 덮어쓰지 않습니다. 작업 시작 시의 출처가 표시되며, 작업별 지침은 사용자가 조정할 수 있습니다.
- `/work-open`과 등록된 workspace의 작업 세션 시작 훅은 빠진 작업 지침·연결 기록을 보완합니다. 기존 버전에서 만든 작업은 `/work-open`으로 먼저 등록하세요. Git 연결이 다른 폴더는 거절합니다.
- 작업의 `.own-harness-work.json`은 저장소 연결 기록입니다. 직접 수정하지 않습니다. 이 기록과 지침은 작업 폴더에만 생성하며 원본 저장소와 코드 worktree에는 추가하지 않습니다.
- `before_agent_start`는 공통 작업 지침, 담당 저장소 지침, 현재 task.md를 전달합니다. 부모가 읽은 AGENTS.md를 omp가 자식에게 자동 상속한다고 가정하지 않고 자식에게도 주입합니다. 작업 지침에 task.md가 작업의 아이디어·설계 정본임을 명시합니다.
- `tool_call`과 `before_subagent_spawn`은 매번 현재 task.md의 목표·범위·비목표·완료 조건·설계 결정과 미정 사항이 비어 있거나 `작성 필요` 등으로 남아 있는지 검사합니다. 실패하면 변경 실행을 차단합니다. 조회 도구와 부모의 task.md·작업 AGENTS.md 보완은 허용합니다. 미완성 상태의 셸은 읽기 명령도 차단합니다.
- 필수 항목이 있어도 일반 `path`를 받는 `write`·`edit`의 checkout 밖 변경, 경로를 벗어나는 이름 변경·심볼릭 링크, 자식의 부모 문서 수정은 차단합니다. 격리하지 않은 서브에이전트는 조회만 가능합니다. URI·경로 별칭·hashline 입력과 `ast_edit`는 현재 경로 검사 대상이 아니므로 일반 파일 `path`를 받는 `write` 또는 지원되는 `edit` 형식을 안내하며 차단합니다.
- 부모의 배정 정보를 자식과 연결할 수 없으면 변경을 허용하지 않습니다. 같은 프로세스에서 같은 부모 ID가 여러 저장소에 연결돼 모호해진 경우도 거절합니다. 저장소별 새 omp 프로세스로 시작하세요.

훅은 표시 파일로 등록된 workspace에만 적용됩니다. 표시가 없는 다른 프로젝트에는 적용하지 않습니다. 이 검사는 문서의 준비 상태를 검사하며 사람의 승인·설계의 적절성을 판정하지 않습니다. 문서 준비 후 허용되는 셸·다른 도구의 모든 파일 접근이나 플러그인을 끈 세션·외부 터미널은 통제하지 않습니다. OS 샌드박스가 아닙니다.

## 기존 서브에이전트·worktree와의 경계

- 플러그인은 `frontend/`, `backend/`의 장기 작업용 worktree만 만듭니다. 기존 `task`, `/wt`, 병합·정리 기능을 교체하거나 중복 등록하지 않습니다.
- 생성한 실행 명령은 **새 프로세스에만** `OMP_WORKTREE_DIR=<작업>/.sub-workspace`를 설정합니다. 실행 중인 부모 세션의 환경이나 전역 `worktree.base`를 바꾸지 않습니다.
- 해당 환경변수는 서브에이전트 격리뿐 아니라 `/wt`, PR checkout, omp worktree 정리에도 적용됩니다. `.sub-workspace` 안에는 사용자가 보관할 문서나 장기 worktree를 두지 않습니다. 내부 이름·배치는 omp가 정합니다.
- 서브에이전트 격리의 활성화·변경 반영 방식은 기존 omp 설정을 따릅니다. 폴더 생성만으로 격리가 활성화되지는 않습니다.
- 현재 omp의 격리 실행은 Git 저장소인 cwd가 필요합니다. `feature-a/`에서 frontend·backend를 한꺼번에 격리하는 기능은 제공하지 않습니다. 저장소별 세션에서 기본 `task` 도구를 사용합니다.
- 작업 문서를 전달하는 것은 실행 통제나 승인 검사가 아닙니다. 사람이 맡긴 범위와 Git 전달 권한은 별도로 유지합니다.

## 검사

```sh
bun test packages/omp
```

임시 Git 저장소로 작업 생성·사용자 확인·이름·원본 보존을 검사하고, 작업 지침 상속·저장소별 문맥·문서 누락·부모/자식 경로 검사를 확인합니다. 실제 모델과의 대화나 서브에이전트 결과 병합 검증과는 구분합니다.
