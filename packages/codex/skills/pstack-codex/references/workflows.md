# 작업별 흐름

필요한 경로와 그 경로가 호출하는 절차만 읽는다. 아래 절차는 사용자 범위를 확장하지 않는다.

## 조사

1. 답해야 할 질문과 확인 가능한 증거부터 정한다. 읽기 전용 요청에서는 제품 코드·설정·Git 상태를 변경하지 않는다.
2. `how`에 해당하는 실제 호출·데이터·상태 흐름을 추적한다. 큰 시스템은 서로 독립적인 2–4개 영역으로 Swarm 조사 후 연결한다. 작은 경로는 한 번의 추적으로 끝낸다.
3. 설계 이유나 회귀 원인이 질문이면 `why`로 Git 변경, 호출자, 설계 문서, 접근 가능한 이슈를 조사한다. 접근할 수 없는 자료는 지어내지 않는다. 현재 동작에서 과거 의도를 추론하면 추론이라고 표시한다.
4. 각 결론에 파일/줄, commit 또는 직접 실행한 결과를 연결한다. 원인 가설을 실제 관찰과 분리한다. 진단 요청이면 수정하지 않고 진단을 전달한다.

## 버그

1. 리드가 수정 전 문제를 원래 CLI/UI/API 등 같은 경로에서 직접 재현한다. 실패 입력, 기대 결과, 실제 결과를 남긴다. 접근하지 못하면 어디까지 확인했는지 기록하고 가능하면 독립적인 조사부터 계속한다. 재현 실패를 성공으로 세지 않는다.
2. 전체 호출 경로와 같은 함수를 쓰는 다른 소비자의 코드를 읽는다. 가설을 구분할 관찰을 택해 원인을 좁힌다. 필요하면 계측한다. 런타임 근거로 원인 메커니즘을 확인한 다음 수정 설계로 넘어간다.
3. 함수 경계를 넘으면 두 설계 스케치를 Arena로 합성한다. 명확한 한 위치의 오류는 그 경계에서 고친다. 증거가 없는 방어 코드와 무관한 정리는 넣지 않는다. 구현 담당자에게 원인 근거와 범위를 전달한다.
4. 원래 재현 입력을 같은 경로에서 다시 실행한다. 영향을 받는 다른 소비자와 필요한 경계 입력도 확인한다. 저렴한 자동 경로가 있으면 수정 전 실패하고 수정 후 통과하는 회귀 검사를 남긴다. 기대값은 구현에서 가져오지 않는다.
5. 실제 출력과 diff를 리드가 확인한다. commit을 만드는 작업이면 재현 검사 → 수정 순서 등 검토자가 이해할 수 있는 작은 단위로 구성한다. 별도 승인 경계까지 필요한 준비를 끝낸다.

## 기능·리팩터링

1. 실제 소비 경로와 설치된 의존성을 조사한다. 리팩터링은 유지해야 할 외부 동작, 기능은 달라질 사용자 동작을 정한다.
2. 호출자의 사용 예를 먼저 쓴다. 그 예에서 데이터 모양, 타입/서명, 소유권과 모듈 경계를 도출한다. 함수 경계를 넘는 변경은 구조가 다른 두 설계안을 Arena로 비교한다. 설계 논쟁이 남으면 Interrogate로 검토한다.
3. 네 항목의 작업 분해 기록(Checkpoint)을 작성한다. 같은 코드가 긴밀하게 연결되면 한 구현 담당자가 소유한다. 독립적인 산출물만 병렬화한다.
4. 선택한 설계를 계약으로 구현을 위임한다. 여러 구현 모양이 여전히 유효하면 구현 후보에도 Arena를 적용한다. 기계적인 반복은 기존 도구 또는 작은 codemod로 처리한다.
5. 각 단위가 끝날 때 실제 계약을 검증한다. 리팩터링은 동작 보존, 기능은 새 동작과 기존 소비자 영향을 확인한다. 계획된 이전 작업(migration)의 임시 실패는 격리된 작업 범위와 복구 지점을 먼저 정한 경우에만 허용한다. 실패 상태를 통과했다고 기록하지 않는다.
6. 반복되는 특수 처리, 타입 우회, 공유 상태가 선택한 설계와 충돌하면 설계를 다시 만든다. 단일 예외만으로 전체를 다시 쓰지는 않는다.
7. 최종 합성 결과와 실제 사용자 경로를 리드가 검증한다. 요청된 전달 형식과 로컬 승인 절차로 마무리한다.

## 성능

1. 기준 ref/작업 파일 상태, 환경, 입력, 실제 완료한 작업량, 측정 단위를 고정한다. 오류나 생략된 작업이 빠른 결과로 계산되지 않게 한다.
2. 프로파일/카운터를 소스 경로에 연결해 병목을 확인한다. 코드만 읽고 병목을 측정했다고 주장하지 않는다.
3. 한 가설씩 적용하고 같은 조건에서 기준과 처리군을 측정한다. 가능한 경우 실행 순서를 섞고 반복 횟수와 분산을 기록한다. 타이머가 실제 비동기 완료를 포함하는지, 캐시나 실패율이 비교를 왜곡하는지 확인한다.
4. 개선을 막는 실제 자원을 설명한다. 제한 요인을 관찰하지 못하면 수치의 해석도 잠정적이라고 쓴다. 단일 샘플이나 몇 번의 agent 실행으로 일반적인 속도·품질 향상률을 주장하지 않는다.
5. 정확성과 원래 사용자 경로를 재검증한다. 지속 개선 요청은 이 단위를 목표까지 반복하며 각 채택/기각과 근거를 기록한다. 개선 없는 변경을 누적하지 않는다.

## Arena

같은 산출물에 대한 대안을 만드는 절차다. 영역 분할과 구분한다.

1. 리드가 동일한 작업 계약과 3–6개 판정 기준을 정한다. 후보에게는 작업 계약만, 판정자에게는 기준도 준다. 각 후보는 자기 작업 경로에만 산출물과 기각한 대안의 이유를 쓴다. 설계는 최소 두 개의 구조가 다른 스케치를 요구한다.
2. 현재 허용된 native 도구로 독립 후보를 실행한다. 각 후보의 입력·쓰기 경로를 분리하고 서로의 결과를 미리 보여 주지 않는다. 모델은 기본 상속한다.
3. 모든 후보가 완료 또는 실패로 종료된 뒤 별도 읽기 전용 판정자를 시작한다. 다른 모델을 실제로 사용할 수 있고 허용되면 그 차이를 활용한다. 같은 모델이면 그 한계를 표시한다.
4. 판정자는 각 후보를 같은 기준으로 평가한다. 동시에 리드도 모든 후보의 실제 산출물을 끝까지 읽는다. 최종 선택은 리드가 한다. 유지보수자가 불변식을 덜 알아도 올바르게 확장할 수 있는 작은 경계를 우선한다.
5. 하나를 기반으로 선택하고 다른 후보의 호환되는 장점만 합친다. 선택·이식·기각·실패한 후보와 이유를 기록한다. 서로 양립하지 않는 방향이면 평균내지 말고 계약을 다시 정한다.
6. 합성 뒤 결과를 새로 검증한다. 후보들의 통과 결과를 합성물의 통과로 재사용하지 않는다.

후보 실패로 두 설계가 확보되지 않으면 필요한 후보를 한 번 보충하거나 두 번째 스케치를 직접 만든다. 둘 다 불가능하면 설계 탐색 부족을 명시한다. 직접 만든 안은 독립 후보라고 부르지 않는다. native 위임이 없는 환경에서는 순차 대안 비교로 진행하되 독립 판정이 없음을 보고한다.

## Swarm

서로 다른 영역을 조사·검증하는 전체 확인 범위를 나누는 절차다. 중복 시도라면 `first pass`, `rank all`, `best-of` 중 선택 규칙을 먼저 정한다.

1. 완료 조건과 전체 영역을 정하고 각 영역에 담당자를 배정한다. 결과를 쓰는 담당자는 고유 출력 경로를 가진다.
2. 같은 공통 계약에 영역별 범위를 더한다. 검증 브리프에는 정확한 ref/파일 상태와 방법을 넣는다. 측정이면 반복 횟수와 샘플 정의도 넣는다.
3. 전 담당자의 결과를 수집한다. 보고는 `PASS`, `ISSUES`, `BLOCKED`와 증거 경로를 포함한다. 기준 ref나 방법이 누락된 결과는 한 번 보완하고, 다시 누락되면 빠진 범위로 남긴다.
4. 리드가 실제 증거를 읽고 중복을 합친다. 필수 영역 하나가 비어 있으면 전체 범위를 확인했다고 하지 않는다. 누락·실패·선택 규칙을 함께 보고한다.

## Interrogate

리뷰 자체의 산출물은 판정이며 자동 수정이 아니다.

1. 사용자 의도, 범위와 정확한 diff/ref 또는 파일 상태를 고정한다. 모든 리뷰어에게 같은 원문과 판정 기준을 준다. 유도하는 기존 결론을 넣지 않는다.
2. native 리뷰어들을 독립 실행한다. 수정·commit·외부 전송은 하지 않도록 작업 범위를 제한한다. 프롬프트의 읽기 전용 계약을 OS sandbox 보장이라고 부르지 않는다.
3. 리드가 모든 지적을 실제 코드·재현 근거와 대조하고 중복·불일치를 정리한다. 표 수만으로 진위를 결정하지 않는다.
4. 각 지적을 `Act on`, `Consider`, `Noted`, `Dismissed`로 판정하고 이유와 증거를 남긴다. 잘못된 지적도 기각 이유를 쓴다.
5. 리뷰 요청이면 판정을 전달한다. 수정까지 허용된 작업이면 판정 이후 실제 문제를 좁혀 고치고 다시 검증한다. 같은 모델의 검토를 원본의 서로 다른 공급자 검토와 동등하다고 주장하지 않는다.
