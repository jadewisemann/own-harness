# 원칙과 적용 조건

원본 24개 principle leaf를 아래 항목으로 재작성했다. 식별자는 원본 파일 이름에 대응한다. 지금의 판단을 바꾸는 항목만 읽고 적용한다. 원본 출처와 실행상 차이는 [upstream.md](upstream.md)에 있다.

## principle-laziness-protocol

추상화나 diff 크기를 결정할 때 적용한다. 삭제·기존 도구·표준 기능부터 찾고, 반복 결정을 한곳에 모으며, 작은 전달 계층과 표현 누수를 줄인다. 가장 작은 변경은 모든 관련 소비자의 원인을 해결하는 변경이다. 좁은 diff를 위해 형제 호출자를 망가진 채 두지 않는다.

## principle-foundational-thinking

로직 전에 데이터 모양과 접근 패턴을 정한다. 여러 단계에 이익이 되는 기반은 먼저, 불필요한 요소 제거는 기반보다 먼저 한다. 구조와 타입을 통일하되 비슷한 몇 줄만을 이유로 추상화하지 않는다. 다른 작업 주체가 같은 상태를 바꿨을 때 영향을 받으면 먼저 격리한다.

## principle-redesign-from-first-principles

새 요구를 붙일 때 처음부터 그 요구가 있었다면 어떤 설계를 택할지 다시 묻는다. 실제 영향 파일과 참조를 읽고 타입·호출자·문서까지 일관되게 반영한다. 전체 설계를 생각하되 전달은 검증 가능한 단위로 한다.

## principle-attack-the-premise

같은 전제를 가진 두 수정이 같은 검증 경계에서 실패하면 다음 수정을 멈춘다. 공통 전제를 한 문장으로 쓰고 작업 주체별 불균형을 재실행 가능한 집계로 확인한다. 특정 작업 주체에 역할을 고정하는 구조가 원인이면 보상 처리를 더하기보다 그 비대칭을 제거한다. 분포가 고르면 그 전제를 원인으로 고집하지 않는다.

## principle-subtract-before-you-add

범위 안에서 불필요한 코드·중복 검사·내용 없는 참조부터 제거하고 더 단순한 기반에 추가한다. 관찰된 사용과 요구를 기준으로 한다. 무관한 정리를 작업에 끼워 넣거나 경계의 필수 검증을 없애는 근거로 쓰지 않는다.

## principle-minimize-reader-load

독자가 추적할 계층 수와 동시에 기억할 변경 가능한 상태를 별도로 줄인다. 같은 인자와 메서드를 그대로 전달하는 계층은 합친다. 반환값과 지역 상태를 선호하고 불변식을 경계 한곳에 모은다. 인터페이스가 충분한 복잡성을 숨기는지는 줄 수와 별개로 판단한다.

## principle-outcome-oriented-execution

계획된 migration은 목표 구조로 수렴시키고 임시 호환 계층을 기본 설계로 남기지 않는다. 임시 실패는 명시된 격리 범위와 복구 지점 안에서만 허용한다. 단위별 검증 경계를 두고 최종 정적·실제 동작 검증까지 마친다. 실패 상태를 green으로 기록하지 않는다.

## principle-experience-first

사용자와 API 소비자, 다음 유지보수자의 경험을 구현 편의보다 우선한다. 기능·옵션마다 핵심 흐름에 필요한 이유가 있어야 한다. 넓고 거친 기능보다 좁고 완성된 동작을 택하고, UX 갈림길은 작은 프로토타입으로 관찰한다.

## principle-exhaust-the-design-space

선례가 없는 상호작용이나 여러 유효한 아키텍처에서는 2–3개 구조가 다른 프로토타입/스케치를 비교한다. 같은 모양의 세부 조정은 별도 설계가 아니다. 정해진 패턴의 기계적 변경에는 불필요한 프로토타입을 만들지 않는다. 함수 경계를 넘는 설계 탐색은 entrypoint의 Architect 계약을 따른다.

## principle-build-the-lever

비단순 작업에는 수행 또는 증명을 다시 실행할 수 있는 파일을 남긴다. 기존 검사·codemod를 먼저 재사용한다. 반복 변환은 첫 단위를 이해한 뒤 가장 작은 안전한 도구로 만들고 재실행해 결과를 대조한다. 한 번의 결정적 도구가 충분하면 수작업 fan-out을 만들지 않는다. 위임 계약은 구현자의 쓰기 범위 밖에 둔다.

## principle-model-the-domain

반복 분기·동기화해야 할 boolean·여러 파일의 모양 가정을 발견하면 도메인의 상태와 소유권을 구조에 담는다. 상태 머신, 모델, 표, reducer, 적절한 collection이나 지식 경계 중 실제 접근 방식에 맞는 것을 택한다. 실행 단계 이름만으로 소유권을 나누지 않는다. 분기·중복·불가능한 상태를 줄이지 않는 추상화는 추가하지 않는다.

## principle-boundary-discipline

CLI·설정·네트워크·외부 API에서 검증하고 도메인 값으로 변환한다. 검증된 내부 값은 반복 검사하지 않는다. 비즈니스 규칙은 가능한 한 순수 함수에 두고 framework 연결은 얇게 둔다. 공개 API에는 transport/storage의 내부 표현 대신 도메인 개념을 노출한다.

## principle-type-system-discipline

불가능한 조합을 표현할 수 없는 타입을 만들고, 의미가 다른 primitive를 구분하며, 외부 입력은 경계에서 파싱한다. variant 추가 시 미처리 지점을 컴파일러가 찾게 하고 권위 있는 schema에서 타입을 도출한다. cast로 검사를 피하지 않는다. 타입 강화는 연산이 partial해지는 지점에 적용하고 정밀함 자체를 위해 복잡하게 만들지 않는다. 동적 언어에서는 컴파일러가 타입을 강제했다고 주장하지 않는다.

## principle-make-operations-idempotent

재시도·재시작되는 변경에는 두 번 실행과 중간 중단 뒤 실행이 같은 올바른 상태로 수렴하는지 확인한다. 상태를 먼저 조회·조정하고 이미 완료된 외부 작업을 중복 실행하지 않는다. stale 상태 정리는 실제 소유·내용 증거와 기존 권한 안에서 한다. 새 실행마다 더 쌓이는 우회 상태를 만들지 않는다.

## principle-migrate-callers-then-delete-legacy-apis

외부 호환성 의무가 없고 조정 가능한 내부 API 변경이면 모든 호출자를 조사·이동하고 같은 변경 단위에서 이전 API를 삭제한다. 임시 adapter는 예외이며 제거 조건을 둔다. 외부 소비자나 버전 계약이 있으면 먼저 확인하고 그 호환성 의무를 지킨다.

## principle-separate-before-serializing-shared-state

동시에 같은 파일·branch·index·상태 객체를 쓰는지 먼저 찾는다. 독립 사실이면 파일·key·worktree부터 분리하고 읽기/합성 경계에서 합친다. 정본 하나가 필요한 경우에만 단일 writer나 실제 lock 등으로 직렬화한다. 파일별 역할을 말로 나눈 것을 concurrency control로 취급하지 않는다.

## principle-prove-it-works

실제 산출물과 값을 직접 확인하고 가능한 검사는 재실행 가능하게 남긴다. 담당자 보고·파일 수정 시각·캐시된 화면·타입 검사만으로 실제 사용자 동작을 추론하지 않는다. 관찰 방식이 틀릴 가능성도 점검한다. 접근하지 못한 surface는 검증 누락으로 남긴다.

## principle-fix-root-causes

먼저 같은 경로에서 재현하고 원인 메커니즘까지 추적한다. 같은 함수의 모든 소비자와 유사 패턴을 확인한다. 증거가 부족하면 계측하고 가설을 좁힌다. 재시작 뒤 결함은 설정·캐시·lock·직렬화 상태도 확인한다. 원인을 밝히지 못한 guard로 증상을 감추지 않는다.

## principle-sequence-verifiable-units

알려진 상태 → 한 변경 → 검사 순서로 단위를 구성하고 통과 또는 명시적 migration 경계 확인 뒤 다음 단위로 간다. commit 작업이면 재현 검사 → 수정, 제거 → 재구성, 기준 측정 → 개선처럼 검토자가 근거를 따라갈 수 있게 한다. 기준 branch를 확인하되 사용자의 미완료 변경이 있는 작업 폴더를 자동 rebase/reset하지 않는다.

## principle-test-behavior-not-implementation

사용자가 호출하는 경로로 실제 대상을 실행하고 관찰 결과를 독립적인 기대값과 비교한다. mock 호출 횟수나 구현의 상수·문자열 재인용만으로 성공을 증명하지 않는다. 결함 있는 구현에서도 통과하는 검사는 고치거나 지운다. 부재를 검사할 때는 대응되는 유효 입력에서의 존재도 확인한다.

## principle-explain-the-number

속도·처리량·품질 수치를 주장하기 전에 실제 완료량, 오류, 캐시, 실행 설정, 반복 횟수와 분산을 확인한다. 프로파일이나 카운터로 제한 자원을 관찰하고 소스에 연결한다. 일부 구간 개선을 전체 개선으로 확대하지 않는다. 행동검증 몇 건은 사례 통과이며 일반적인 품질 개선률이 아니다.

## principle-guard-the-context-window

큰 로그·문서·독립 조사 결과는 필요하면 담당자에게 넘기고 리드는 결론과 증거 경로를 유지한다. 매번 필요한 짧은 계약은 entrypoint에 두고 조건부 상세만 참고 파일로 분리한다. 단계와 출력 크기를 제한하며 같은 대형 파일을 반복해서 읽지 않는다.

## principle-never-block-on-the-human

이미 허용된 되돌릴 수 있는 작업은 합리적으로 결정하고 구체적인 결과를 보여 준다. 관찰할 수 있는 사실을 사람에게 결정해 달라고 하지 않는다. 필수 제품 선택·사용자가 정한 승인·권한 확대는 기다린다. 기다리는 동안 독립적인 허용 작업은 계속한다. 시간 경과나 무응답은 승인이 아니다.

## principle-encode-lessons-in-structure

반복되는 수정은 같은 지시를 더 쓰기보다 타입·lint·기존 helper·runtime 검사 중 실제로 막을 수 있는 가장 강한 작은 수단에 반영한다. 일회성 사건을 전역 규칙으로 일반화하지 않는다. 구조적 해결이 있으면 중복 지시는 덜어낸다. 개인 memory나 전역 설정 변경은 별도 사용자 권한을 따른다.
