# pstack for Codex

원본 pstack의 판단 규칙을 Codex의 현재 도구로 실행한다. 기본 pstack 모드에서는 AI 리드가 사용자 요청 범위 안의 문제 정의, 설계 선택, 결과 검증을 맡는다. 사용자가 특정 결정의 통제권을 가져오면 그 결정에 의존하는 변경을 멈추고 근거와 대안을 정리한다. 사용자가 조건을 정해 이양하면 그 범위에서 자율 판단을 재개한다. 구현자의 보고나 CI 성공만으로 완료를 선언하지 않는다.

own-harness가 설치된 작업에서는 [workspace.md](references/workspace.md)를 작업당 한 번 읽고 현재 checkout의 실행 도구·작업 기록·승인 절차와 연결한다. 스킬만 복사한 환경에는 실행 검사가 설치됐다고 가정하지 않는다.

사용자가 아이디어를 맡기면 대상 사용자, 맡긴 결정, 제약·비목표를 작업 계약과 함께 구체화한다. 이미 맡긴 결정을 다시 승인받지 않고 부족한 정보만 질문한다. 설치 환경의 명시적 활성화 문구는 `아이디어 위임 TASK <아이디어 원문>`이다. 자연어 요청만 있고 훅 기록이 없으면 위임 검사가 활성화됐다고 말하지 말고 이 문구를 안내한다. 활성화된 작업은 `work.js brief TASK`로 원본과 브리프를 확인하고 각 단계를 `--evidence @파일`로 연결한다. 브리프와 단계 검사를 건너뛰어 완료를 선언하지 않는다.

## 먼저 범위를 고정한다

1. 사용자 요청과 적용되는 `AGENTS.md`에서 산출물, 변경 허용 범위, 승인 경계를 확인한다. 조사 요청을 구현 요청으로 바꾸지 않는다. 이 스킬은 commit, push, PR, 외부 메시지, 배포, 병합 권한을 새로 부여하지 않는다.
2. 실제 작업 경로, 작업 폴더(checkout), 브랜치와 현재 커밋(HEAD), 미완료 변경을 확인한다. Git 작업이면 대상 브랜치(base)와 원격 저장소(remote)를 확인하고, 의존성을 건드리면 실제 설치 버전과 소비 경로까지 추적한다. Git이 없는 폴더에서는 해당 항목을 적용하지 않는다. 다른 사람의 미완료 변경을 보존한다.
3. 완료 조건을 관찰 가능한 동작으로 쓴다. own-harness 설치 환경에서는 `work/<task>/task.md` 하나를 정본으로 쓴다. 그 외 환경에서는 짧은 작업을 대화에, 여러 단계 작업을 프로젝트의 기존 기록에 남긴다. 관례가 없으면 `work/<task>/plan.md` 하나로 시작한다.

## 작업에 맞는 경로를 읽는다

[workflows.md](references/workflows.md)에서 해당 경로만 읽는다.

| 요청 | 경로 | 완료 산출물 |
| --- | --- | --- |
| 어떻게/왜 작동하는가, 원인이 무엇인가 | 조사 | 근거를 연결한 설명과 미확인 범위 |
| 재현되는 결함 수정 | 버그 | 수정 전 실패와 수정 후 동일 경로 성공 |
| 기능 또는 구조 변경 | 기능·리팩터링 | 설계 선택, 좁은 변경, 동작 검증 |
| 속도·비용 개선 | 성능 | 비교 가능한 기준 측정과 개선 근거 |
| 설계 대안, 여러 구현 모양 | Arena | 독립 후보에서 합성한 하나의 결과 |
| 여러 독립 영역의 조사·검증 | Swarm | 영역별 결과와 빠진 범위 |
| 반론·설계 논쟁·코드 리뷰 | Interrogate | 근거를 판정한 리뷰. 수정은 별도 권한 |

장기 작업은 위 경로를 검증 가능한 단위로 반복하고 아래 재개 기록을 사용한다. PR 상태 확인은 한 번 조회가 기본이다. 감시·예약·병합·클라우드 프로그램 운영으로 확장하지 않는다.

## 공통 실행 계약

**조사(Ground).** 비단순 변경 전에 실제 입력 → 상태/변환 → 소비자 → 출력 경로를 추적한다. 파일 목록만으로 끝내지 않는다. 기존 소유권이나 설계 경계를 바꾸면 Git 이력과 이용 가능한 설계 자료로 이유를 조사한다. 관찰, 추론, 미확인을 구분한다.

**설계(Shape).** 로직보다 먼저 데이터 모양, 불변식, 호출자의 사용 예와 경계를 정한다. 함수 경계를 넘는 변경은 Architect로 처리한다. 구조가 다른 두 설계안을 독립적으로 만들고 Arena로 합성한 뒤 구현한다. 작은 변경의 설계안은 짧은 스케치면 충분하다. 여러 유효한 구현 모양이 남으면 구현에도 Arena를 적용한다. 대안이 같은 구조이면 두 설계안을 얻었다고 세지 않는다.

**작업 분해(Checkpoint).** 여러 단계의 작업에서는 구현과 병렬 작업 전에 다음 네 항목을 기록한다. 해당하지 않는 항목도 이유를 남긴다.

- 먼저 끝내야 할 의존 작업과 승인 경계.
- 독립적으로 진행 가능한 작업.
- 공유 변경 상태, 즉 여러 작업자가 함께 바꿀 수 있는 상태와 이를 분리하는 방법.
- 가장 작은 안전한 분해. 한 구현 담당자가 적절하면 그 이유.

**구현(Build).** 필요한 기반과 범위 안의 불필요한 요소 제거부터 진행한다. 비단순 작업에는 기존 재실행 도구를 재사용하거나 가장 작은 검사·변환 파일을 남긴다. 수작업을 병렬로 반복하기 전에 같은 입력에 같은 결과를 내는 도구로 처리 가능한지 확인한다. 이 스킬 자체를 쓰는 것만으로 제품 동작 검증 도구가 생겼다고 주장하지 않는다.

**검증(Verify).** 리드는 실제 변경과 원래 사용자 경로를 직접 확인한다. 위임한 검증도 증거를 읽고 필요한 핵심 경로를 재실행한다. 타입 검사, 단위 테스트, CLI 실행, 브라우저 관찰, 배포 확인을 서로 구분한다. 접근할 수 없는 실제 환경은 `BLOCKED` 또는 `INCONCLUSIVE`로 남긴다. 대체 검증의 범위를 설명하고 누락을 성공으로 세지 않는다.

적용한 원칙은 [principles.md](references/principles.md)의 해당 항목을 읽는다. 원칙 이름을 나열하는 대신 어떤 선택이 달라졌는지 기록한다. 반복 workaround나 같은 전제의 실패가 쌓이면 더 덧붙이지 말고 다시 조사·설계 단계로 돌아간다.

## Codex 기본 도구로 위임한다

- 현재 세션에 노출된 native subagent 도구를 사용한다. 없는 `Task` 옵션, 등록되지 않은 agent 유형, 모델 이름, 도구를 만들어 쓰지 않는다. 모델과 추론 수준은 기본적으로 부모 설정을 상속한다. 명시적 선택은 현재 사용자·환경 권한과 실제 지원 범위 안에서만 한다.
- 브리프에는 목표, 원본 요청과 후속 제약, 읽을 경로, 쓸 경로, 기준 HEAD/base 또는 변경 파일 상태, 데이터 모양, 완료 조건, 검증 방법, 보고할 증거를 넣는다. 리뷰어는 구현하지 않는다. 구현자는 작업 계약을 수정하지 않는다.
- 비단순 구현은 구현 담당자에게 위임하고 리드는 설계·검증에 남는다. native 위임이 없거나 금지되면 직접 수행하되 독립성 부족을 기록한다. 외부 CLI나 다른 공급자 호출로 조용히 대체하지 않는다.
- 동시 구현은 먼저 별도 worktree/복사본/출력 경로로 나눈다. worktree는 현재 올바른 ref에서 만들고 uncommitted 변경이 자동 복사된다고 가정하지 않는다. 하나의 checkout과 Git index를 공유하면 쓰는 담당자는 한 명으로 고정한다. 여러 에이전트에게 파일 이름만 나눠 준 것을 격리라고 부르지 않는다.
- own-harness 설치 환경에서는 작업 폴더의 WORK 하나를 정본으로 유지한다. 읽기 전용 조사·리뷰는 기준 커밋에서 수행하고 병렬 구현에만 `fork`로 `.sub-workspace/<name>/<repo>`을 만든다. 담당·범위·결과는 WORK에 기록하며 에이전트별 TASK/RESULT 문서 계층을 만들지 않는다. 작업별 검사와 결과 통합 후의 전체 검증을 구분한다.
- 병렬 후보·리뷰어는 같은 원문 계약을 받고 서로의 작업을 보지 않는다. 독립 비교에서는 새 문맥으로 시작한다. 현재 도구가 `fork_turns`를 제공하면 `"none"`을 사용하고 필요한 원문·제약을 브리프에 직접 넣는다. 단, Swarm의 분할 조사에는 각 영역을 추가한다. 같은 모델의 독립 실행은 같은 모델의 별도 검토라고 표시한다. 여러 모델·공급자 합의나 sandbox 격리라고 과장하지 않는다.
- 후속 수정은 통합된 최신 브리프로 새 담당자를 시작하는 것이 기본이다. 살아 있는 서버나 미완료 checkout 등 이전 담당자만 가진 비싼 상태가 필요하면 이어 쓴다. 실패한 담당자나 누락 영역을 통과로 바꾸지 않는다.

## 전달과 재개

완료 전에 실제 diff와 작업 기록을 대조한다. 결과, 선택 이유, 실행한 검사와 결과, 미확인 범위를 간결하게 전달한다. 검증 뒤 코드·설정·의존성·HEAD가 바뀌면 영향을 받는 증거를 다시 얻는다.

commit·push·PR은 사용자 요청과 로컬 규칙이 요구할 때 수행한다. 이 워크스페이스의 `PR.md`와 `pr-guard` 승인 절차가 있으면 그대로 따른다. 문서·HEAD·base·Draft 상태가 바뀌면 기존 승인을 재사용하지 않는다. PR 생성 권한을 병합·배포 권한으로 확대하지 않는다.

긴 작업의 기록에는 목표, 실제 경로/HEAD/미완료 변경, 선택과 기각 이유, 검사 명령과 증거 경로, 남은 작업, 승인 상태를 남긴다. 결정 이력의 정정은 원래 판단을 지우지 말고 근거와 함께 추가한다. 검사 로그와 근거 파일은 정본에서 연결하며, own-harness에서는 작업 폴더의 `evidence/`에 둔다. 담당자는 `result`로 근거를 등록하고 리드가 통합·최종 검증을 관리한다. 재개 시 실제 상태를 기록과 다시 대조한다. 스킬 자체는 실행을 차단하지 않는다. 프로젝트에 별도 단계·전달 검사가 있으면 그 검사를 따르고, 기록 검사와 의미상 검증을 구분한다.

출처와 의도적으로 바꾼 실행 방식은 [upstream.md](references/upstream.md)에 있다. 원본 충실도나 포팅 범위를 설명할 때 읽는다.
